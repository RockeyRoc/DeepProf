## 2. 每个数字是怎么测出来的

### 2.1 冷启动耗时（图 1）

脚本 `bench_startup.py`。每个模式**先跑 1 次热身并丢弃**（第一次运行要读几百 MB 的
dll / JS，全是冷文件缓存，不丢的话第一个数永远是离群值），然后 prod 测 5 次、dev 测 3 次。
每次之间间隔 1.5 秒。

两个口径，各自量的是不同的东西，**不能混着引用**：

- **外部计时（wall）**：harness 调 `Popen` 之前记一次 `perf_counter`，到读到日志里
  「窗口已显示」那一行为止。包含了 npm / electron-vite 外壳的开销，对应**用户双击
  `.bat` 的体感**。
- **内部计时（internal）**：主进程自己用 `process.uptime()` 反推出进程出生时刻，
  到窗口显示为止（`raw` 里的字段名是 `internal_window_shown_ms`，脚本注释里对应
  `did-finish-load`）。不含外壳开销，是**应用本身**的冷启动。

| 模式 | 次数 | 外部计时中位数 | 外部最小–最大 | 内部计时中位数 | 内部最小–最大 | 外壳开销中位数 |
|---|---|---|---|---|---|---|
| 生产 prod（打包产物） | 5 | **478.6 ms** | 469.8 – 551.3 | **437.0 ms** | 432.4 – 510.9 | 37.8 ms |
| 开发 dev（`npm run dev`） | 3 | **1394.7 ms** | 1392.8 – 1495.8 | **489.9 ms** | 487.7 – 551.5 | 905.8 ms |

说明：

- 「外壳开销」= `startup_runs.csv` 里 `spawn_overhead_ms` 列的中位数，即
  `Popen` 到 Electron 主进程真正出生之间的时间。这一列是原始测量列，本节只是对它取了
  中位数（prod 5 个值：34.6 / 37.8 / 36.7 / 37.9 / 39.3；dev 3 个值：905.8 / 902.5 / 944.3）。
- 结论只有一句：**开发模式慢在 npm / electron-vite 外壳上，不慢在应用本身** ——
  两种模式的内部计时只差约 53 ms（437.0 vs 489.9）。开发时启动要等 1.4 秒属于正常现象，
  不是程序有问题。
- p95 只在 `startup_summary.json` 里有：prod 544.3 ms、dev 1485.7 ms。5 个和 3 个样本
  算 p95 意义有限，这里照录，不做解读。
- 每次的原始读数（含 `process_start_epoch`、判定用了哪一行日志）在 `raw/startup_runs.csv`。

### 2.2 打包体积（图 2）

脚本 `bench_bundle.py`。对目录树**逐文件累加 `os.path.getsize`**，是静态统计、单次执行，
不涉及采样。1 MB = 1024 × 1024 字节。

`out/` —— 这是要交出去的东西：

| 项 | MB | 字节 | 文件数 |
|---|---|---|---|
| out/ 合计 | 6.87 | 7,202,337 | 43 |
| 　out/main（主进程） | 0.03 | 33,864 | 1 |
| 　out/preload（预加载桥） | 0.002 | 2,110 | 1 |
| 　out/renderer（渲染进程） | 6.83 | 7,166,363 | 41 |
| 　　↳ 其中 Live2D 官方样例模型 | 3.90 | 4,085,969 | 33 |
| **扣除 Live2D 样例后的交付体积** | **2.97** | 3,116,368 | — |

- 「扣除 Live2D 样例后的交付体积」是**算出来的差值**（7,202,337 − 4,085,969），
  不是目录遍历的结果，所以 `bundle_size.csv` 里它的 `files` 列记为 0。别当成"0 个文件"。
- 为什么要把 Live2D 拆出来：`out/` 里超过一半是 Live2D 官方的 Haru / Shizuku 样例模型，
  按《素材授权调研》的结论它们**只在开发期用来验证渲染链路，不进最终交付物**。
  不拆的话，看到「桌宠 7 MB」会以为交付体积就该这么大。
- `out/main` 只有 33 KB、`out/preload` 只有 2 KB。preload 的 2110 字节在
  `bundle_size.csv` 的 MB 列被四舍五入成 0.0，读数没意义，所以上表和图表都按字节重算为
  0.002 MB。因为 0.002 MB 根本画不出柱子，图 2 里直接标注「太小，画不出柱」并把数值写在
  原位，没有画成一条假线。

`node_modules/` —— **不进交付包**（构建时只把 renderer 真正 import 到的模块打进去），
列出来是为了回答「为什么装一次依赖要几百 MB」：合计 **357.71 MB / 5,595 个文件**，
其中 `electron` 一个包就占 **269.02 MB（75.2%）**，是 Electron 方案把 Chromium + Node
一起打包的固有代价。

`src/` 源码合计 15.31 MB / 67 个文件。完整清单见 `raw/bundle_size.csv`。

### 2.3 运行内存（图 3）

内存是随时间长的，所以**必须说清是哪个时刻的数**，这里给两个口径。

**外部口径**（`bench_insitu.py` 的后台线程，每 3 秒一次）：用 PowerShell
`Get-Process electron` 按可执行文件路径过滤（`*DeepProf*`，避免把用户开着的 VS Code /
Discord 也算进来），累加全部 electron 进程的 Working Set。采样跨 2 次启动，
run 1 拿到 11 个点、run 2 拿到 30 个点，共 41 个。

- 启动爬升：进程数从 2–3 个涨到 5 个，内存从约 92 MB 爬到 500 MB 以上。
- **稳态（进程数起满 5 个之后的 37 个采样点）：517.6 – 547.6 MB，中位数 539.0 MB。**

**内部口径**（`raw/_smoke.json`，被测进程内的探针用 Electron `app.getAppMetrics()` 读数）：
带进程角色标注，能分开报主进程 / 渲染进程 / GPU / Utility。**单次完整样本（n = 1）**。

| 采样时刻 | 主进程 Browser | 渲染进程 Tab | GPU | Utility（合计） | 合计 |
|---|---|---|---|---|---|
| t0 窗口刚显示（0.6 s） | 92.8 | 83.6 | 114.1 | 50.1 | **340.6** |
| t8s 稳态（10.1 s） | 119.3 | 120.8 | 171.1 | 128.2 | **539.4** |
| t15s 延迟测量前（16.6 s） | 119.3 | 129.7 | 166.5 | 128.2 | **543.7** |
| t60s 测量结束（75.5 s） | 119.5 | 125.1 | 168.8 | 128.3 | **541.7** |

- Utility 一栏是**同角色多个进程的合计**：t0 时只起来了 1 个 Utility，稳态后有 2 个
  （50.1 → 50.1 + 78.1 = 128.2）。图 3 下图里 t0 的 Utility 段只有 22 px 高，
  数值仍标在段内。
- 稳态后内存基本不再增长：t8s 到 t60s 之间（65 秒）合计只从 539.4 变到 541.7 MB，
  波动在 ±5 MB 内。
- **两个口径互相验证**：进程内 539.4 MB vs 外部 517.6 – 547.6 MB，吻合。
  这是两个独立测量路径（应用自报 vs 外部 PowerShell），能对上说明内存口径没搞错。
- 进程数从 2–3 个涨到 5 个是正常的 Electron 多进程结构（主进程 / 渲染 / GPU / Utility
  各自独立进程，起来有先后）。**这是进程结构，不是内存泄漏。**

### 2.4 事件响应延迟（图 4）

`raw/_smoke.json`，**单次完整样本（n = 1），6 轮问答**。每轮注入一条问答事件，
记录从注入到 DOM 变更、到首帧上屏的时间。时间戳跨进程对齐用了 `clock_skew_ms`
（6 轮分别为 2.377 / 2.434 / 2.315 / 2.396 / 2.343 / 2.396 ms）。

| 轮次 | send → DOM 变更 (ms) | send → 首帧上屏 (ms) | 该轮气泡文本 |
|---|---|---|---|
| 第 1 轮 | 503.37 | 507.77 | 「你问的」 |
| 第 2 轮 | 1.74 | 2.34 | 「思考中」 |
| 第 3 轮 | 1.92 | 2.42 | 「思考中」 |
| 第 4 轮 | 1.35 | 2.75 | 「思考中」 |
| 第 5 轮 | 1.22 | 2.82 | 「思考中」 |
| 第 6 轮 | 1.13 | 2.33 | 「思考中」 |

- **第 1 轮的 503.37 ms 不能代表稳态**，两个理由：该轮气泡文本是「你问的」，
  与第 2–6 轮的「思考中」不是同一条 DOM 变更路径；且属首次触发，含一次性的
  编译/JIT 成本。**引用时请用第 2–6 轮的区间。**
- 稳态区间（第 2–6 轮）：DOM 变更 **1.13 – 1.92 ms**，首帧上屏 **2.33 – 2.82 ms**。
- 另有 12 次 IPC 往返测量（`ipc_roundtrip`）：最小 0.6 ms、中位数 0.9 ms、最大 2.8 ms。
  样本少，只作参考。

## 3. 测到了、但不能当作性能结论的部分

`raw/_smoke.json` 里有一组帧率与绘制调用数据，**本轮不适合用来证明渲染性能**，原因如下：

| 指标 | 空载 | 流式输出中 |
|---|---|---|
| rAF 帧率 | 239.95 fps | 240.18 fps |
| 绘制调用/秒 | 29.4 | 29.7 |
| 每帧绘制调用 | 0.122 | 0.124 |
| 画布尺寸 | 222 × 302（CSS 同尺寸，DPR 1.5） | 同左 |

- 240 fps 就是显示器 240 Hz 的刷新率本身，说明 rAF 没有被节流，
  **不等于**"渲染性能达到 240 fps"。
- 每帧只有 0.12 次绘制调用 —— 也就是**大部分帧什么都没画**。
  同一份数据里 `pixi_shared_ticker.started = false`、`FPS` 是未修改的默认值 60
  （`is_default_value: true`），说明 Pixi 的 ticker 当时根本没启动。
- `raw/insitu_run1.log` 里的渲染诊断也印证了这点：
  `{"rootLen":203,"hasPet":false,"petSrc":null,...}` —— 没找到桌宠元素，图片源为空。
  （注意：这条诊断属于另一次运行，不是 `_smoke.json` 那一次，只能作为旁证。）

**所以：本轮没有测到"角色真正渲染起来之后"的帧率与绘制开销。** 详见第 4 节。

### 其它已知限制

- 测量期间有人在改渲染层代码（见上），被测产物与最终提交版本**不保证完全一致**。

## 5. `startup_runs.csv` 与 `startup_summary.json` 的一致性核对

**结论：两者逐项一致，不存在冲突，无需以任何一方为准。**

核对方式（`make_charts.py` 每次运行都会自动做一遍，结果打印在控制台）：
把 `startup_runs.csv` 里每个模式、每个字段的逐次读数，与 `startup_summary.json`
的 `samples` 数组**按顺序逐项比对，容差 0.05 ms**。两种模式 × 2 个字段全部一致。
summary 里的 min / median / p95 也与 CSV 原始值重算的结果一致
（median：样本数为奇数时取排序后中间那个，偶数时取中间两个的平均；p95：线性插值）。

### 6.1 图 1 的口径错误（已在开头 banner 更正）

### 6.2 「Pixi 的 ticker 当时根本没启动」——这条解读是错的

本文档 §3 用 `pixi_shared_ticker.started=false` 当作「角色没渲染」的证据。
但**探针作者自己在 `desktop/src/main/index.js:1190-1197` 写了**：本项目用的是
`Application` 自建 ticker，`Ticker.shared` **从来就没启动过**，它的 FPS 是构造默认值，
注释原话是「**别当数据用**」。不能拿它证明任何事。

### 6.3 帧率那段可能读反了

§3/§4 据 `每帧 0.122 次绘制` 推论「大部分帧什么都没画」。
但原始数据是 **147 次 draw 对应 147 次 clear，5 秒内每秒 29/30/29/30/29** ——
这正是一个 **~30 fps 渲染循环**的形态，不是「没画」。

而且 `RigPet.jsx:111-117` 的注释记载：这里**曾经设过 `maxFPS = 30`**（后来才去掉）。
被测版本很可能就是带 `maxFPS=30` 的那个。

另外 `draws_per_frame` 的分母用的是探针自己的 rAF 循环（240 Hz），
拿它当分母本身就会把比值压得很低。

**更可能的结论是「角色在渲染，但只有 ~30 fps」** —— 一个真实且不好看的数字，
而不是「没测到角色渲染」。

### 6.4 第 1 轮延迟（~500 ms）应当作废重测，而不是"解释掉"

§2.4 用「不是同一条 DOM 变更路径」把第 1 轮排除。这条理由是**推测、无证据**。

反证：探针源码注释写第 1 轮「**稳定地**是 ~500 ms」——能稳定复现，就说明那是
用户每次问第一句时**真实会遇到**的数字，不该被排除。

而且证据字段 `evidence_bubble_text` 抓到的是 **"你问的"** 三个字，
这个字符串在渲染层源码里**不存在**（最接近的是主进程 Mock 模板
`你问的是「${short}」`，`main/index.js:120`）。也就是说那一轮抓到的是
**流式输出的第 3 个字符**，不是 loading 态出现。

**正确处置是把这一轮标为无效并重测**，而不是既把它画进图 4 左图、
又反过来拿它当排除第 1 轮的理由。

### 6.5 其它

- **复现链是断的**：`_smoke.json` 的 6 个 latency 条目没有 `long_tasks` 字段、
  meta 里没有 `source_hashes`，而当前源码 `index.js:1570` / `:1342` 是**必写**的。
  说明这份样本出自更早的探针版本 —— **没人能用仓库里的代码复现这份 n=1 样本**。
  而 `source_hashes` 这个机制存在的唯一目的，正是回答"这数是什么版本测的"。
- **延迟的修正量比被测量还大**：`send_to_dom = raw − t_send − clock_skew`，
  6 轮原始差 3.1–5.2 ms，skew 修正 2.3–2.4 ms，结果才 1.13–1.92 ms。
  skew 的误差来自链路不对称且**从未量化** —— 在这个量级报两位小数是**虚假精度**，
  相对不确定度可能到 30–50%。
- **"两个口径互相验证"（§2.3）夸大了**：进程内与外部两组的 **PID 完全不同**，
  是两次不同启动在稳态处的横向比较，不是同一次测量的互验。
- **"冷启动"名不副实**：每个模式先热身 1 次并丢弃、样本间隔 1.5 秒 ——
  这是**热文件缓存**下的启动。§4 承认没采真实首启，但图 1 标题与 §2.1 仍叫"冷启动"。
- **外部内存 run 1 只有 11 个点、跨度 32 秒**，而一次完整 bench 要跑约 76 秒
  （`_smoke.json` 的 `t60s` 快照在 75.5 s）。一份"成功"的 run 不可能只有 32 秒采样 ——
  这份 CSV 要么出自另一个版本的脚本，要么 run 1 其实中途异常退出但留下了 JSON。
  本文档只写了"11 个点 / 30 个点"，没解释这个不对称。
- **`t_mut` 不是 DOM 真正变化的时刻**：`MutationObserver` 回调是微任务、
  记录里没有时间戳，`firstMut` 记的是**回调跑起来的时刻**，渲染进程一忙就整体偏大。

### 6.6 复核中确认**做对了**、应当保留的部分

- 内存口径明确写了是 Working Set（`workingSetSize` / `WorkingSet64`），不是 private bytes；
  稳态下限只用「进程数起满 5 个」之后的采样点，并说明了为什么不用启动瞬间的 91.8 MB；
- §4 明确写了不能从「65 秒 ±5 MB」推断没有内存泄漏；
- 帧率结论选择**不出图**（虽然理由是错的，但不出图这个选择本身是稳的）；
- `make_charts.py` 四张图纵轴**都从 0 开始**；图 1 用中位数 + 最小最大竖线并标了 n；
- 缺数据直接 `raise` 不填默认值；§5 的自我一致性核对是真做了的。

```
│   ├── 01_冷启动耗时.png        生产 / 开发两种模式 × 外部 / 内部两种口径，含最小–最大范围

└── raw/                   原始数据，未经修改
    ├── startup_runs.csv         冷启动 8 次逐次读数（prod 5 + dev 3，另有 2 次热身未落盘）
    ├── startup_summary.json     冷启动汇总（min / median / max / p95）
    ├── bundle_size.csv          体积逐项清单
    ├── bundle_size.json         体积汇总
    ├── memory_external.csv      外部内存采样 41 点（2 次启动）
    ├── _smoke.json              进程内探针完整样本（n = 1）：内存 / 帧率 / 延迟 / IPC
    └── insitu_run1.log          稳态实测第 1 次的应用日志（该次未产出 JSON）
```

重新生成图表：

```bash
cd 性能数据
python make_charts.py
```

脚本只依赖 `Pillow`（本机 12.3.0）和标准库。**本机没有 matplotlib，项目也没有经费，
所以图表是用 Pillow 按 2 倍超采样手绘后缩放的，没有安装任何新依赖。**
中文字体用 `C:\Windows\Fonts\msyh.ttc`。

脚本对缺数据的处理方式是：**文件不存在或字段缺失就直接报错退出，不填默认值、不补数字。**
`raw/` 目录本包内没有被修改过。
