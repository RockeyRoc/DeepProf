## 场景 1：模型失败（`model.failed`）

### 怎么复现

打开对话面板 → 点 **`报错`** 按钮。

### 预期现象

事件序列（可在事件日志里逐条对）：

```text
session.started {resumed:false}
agent.turn.started {input:"帮我讲讲数据库第三范式"}
pedagogy.node.entered {node:"Assess"}
── 约 500ms ──
model.requested {provider:"deepseek", model:"deepseek-chat"}
── 约 700ms ──
model.failed {code:"RATE_LIMIT", message:"模型服务限流"}
agent.failed {reason:"provider", retryable:true}
```

界面上：

- 气泡先显示一句 loading 台词（`persona.js` 随机挑，如「唔…我想想。」）带三个跳动小点，
  约 1.2 秒后变成一句 error 台词（如「啧，掉线了。要我再试一次吗？」）。
- 聊天面板的消息区**新增两条系统消息**（从上到下）：
  1. `模型失败：模型服务限流`（来自 `model.failed`，取 `message`，没有 message 时退回 `code`）
  2. `本轮失败：provider`（来自 `agent.failed`）
- `取消` 按钮**消失**（它只在 `loading` / `streaming` 状态出现）。
- 没有语音：本轮从未收到 `model.completed`，不会触发朗读。
- 事件日志里 `model.failed` 与 `agent.failed` 的 `source` 都是 `runtime`。
- 气泡**不会自动收起**（`error` 状态下一直挂着，直到开始新一轮）—— 见「已知偏差」。

### 为什么算通过

1. **两层错误被如实区分**：模型层的失败（`model.failed`）和本轮运行的失败（`agent.failed`）
   各产生一条消息，看消息就知道是"模型挂了"还是"这一轮废了"。这正是 §7.3「Provider 失败：
   按能力与成本策略切换备用模型，Graph 无需改动」所依赖的信息分层。
2. **状态机没有卡死**：报错后再点 `正常回复`，必须能正常走完一轮（气泡变流式文本并朗读）。
   这是本场景真正的判据 —— **失败之后还能继续用**。
3. **不误报成功**：全程没有出现 `model.completed`，所以不会把空回复当成一次成功回答入库。

### 已知偏差

- 错误文案是 `persona.js` 里写死的几句（「掉线了」「刚才断了」「没连上」），
  **没有真的重试按钮**，`retryable:true` 这个字段前端也没用（一律按可重试处理）。
- 气泡在 `error` 状态下不自动收起（显示条件里有 `status !== 'idle'`）。

## 场景 2：用户取消（`agent.failed {reason:'cancelled'}`）

### 怎么复现

有两条路径，**都要走一遍**：

- **2-A 回复中取消**：点 `正常回复` → 等气泡开始逐字出现（约 0.5 秒后开始；整轮约 9~10 秒）
  → 在**任意一个教学节点**的吐字过程中点 **`取消`**。
- **2-B 加载中取消**：点 `加载中` → 状态停在「思考中…」→ 点 **`取消`**。

### 预期现象

事件序列：

```text
…（已发出若干 model.stream.delta，可能停在 6 段中的任意一段）…
agent.failed {reason:"cancelled", message:"本轮已取消"}   ← source = "renderer"
session.compacted {reason:"cancelled"}
```

界面上：

| | 2-A 回复中取消 | 2-B 加载中取消 |
| --- | --- | --- |
| 气泡 | 一句 cancelled 台词（如「行，那先停这儿。」） | 同左 |
| 消息区 | 新增一条 pet 消息：`<已流出的那部分文本>（已中断）` —— **已产出的文字不丢** | **不新增任何消息**（还没有任何 delta，缓冲为空） |
| 语音 | 点下去**立刻**停（本地先 `stop()`，不等 IPC 返回） | 本来就没在念 |
| `取消` 按钮 | 消失（状态已离开 `loading`/`streaming`） | 消失 |
| 动画 | 切到 `sad`（`STATUS_TO_ANIMATION.cancelled = 'sad'`） | 同左 |
| 事件日志 | `agent.failed` 的 `source` 显示 **`renderer`** | 同左 |

> ⚠️ 2-A 有一个**容易误判为 bug 的现象**：取消时如果正好停在两个节点之间的停顿里，
> 气泡里显示的是**上一个节点的完整文本**（因为 `streamRef` 保留着最后收到的 delta）。
> 这不是故障 —— 停顿时 `delta` 已经收完，只是下一个还没开始。

### 为什么算通过

1. **§16.4 验收项「流式文本与语音可停止」**：文本停在按下取消的那一刻，**已经吐出来的部分
   不会丢**（带「（已中断）」入库），语音立刻中断且不残留 —— 这就是「可中断播放」。
2. **取消后可继续**：紧接着点 `正常回复`，能走完一轮新对话。状态机没有卡在 `cancelled`。
3. **语音不会"穿越"**：取消后不应再听到上一轮的声音。`tts.js` 用 `generation` 计数丢弃
   被取消 utterance 的回调，且 `stop()` **同时停掉两个引擎**
   （神经语音走 `<audio>`、系统语音走 `speechSynthesis`）—— 只停一个的话另一个会继续念。
4. **取消是用户主动行为，语义不丢**：`source` 为 `renderer` 能看出这一条是前端发起后
   由 Runtime 回流的事件，状态来源仍然单一（不是前端自己直接改状态）。

### 已知偏差

- `cancelled` 复用了 `sad`（难过）表情 —— 用户主动取消却被表现得像出错，
  和 `error` 视觉重复。设计上更合理的是平静表情或待机。**这一条从 v0.4 时代记到现在，未改。**
- 取消时 Mock 额外发了一条 `session.compacted`，而这个事件名的语义是「上下文压缩」，
  与取消无关，属语义误用。**未改。**
- 一个**界面上不可达**的边界：若本轮已经结束（内部 `traceId` 已清空）再调取消，
  IPC 会返回 `ok:false` 且**不产生任何事件**，界面不会有任何变化。此时 `取消` 按钮本来
  也已经隐藏了，所以点不到 —— 只有在直接调用 IPC 时才会遇到这个分支。

## 场景 3：断线重连**不重复展示**（`session.resumed`）

### 怎么复现

**不需要真的断线** —— 任何时候点 **`重连`** 按钮即可（这是 Mock 的定时器模拟）。

### 预期现象

事件序列：

```text
session.resumed {resumed_from:"sess_..."}                      ← trace_id 为 null
── 约 900ms ──
model.completed {text:"会话已恢复，可以继续。"}                  ← 前面没有任何 delta
agent.turn.completed {status:"ok"}
```

> 注意第二条**没有前置的 `model.stream.delta`**（不像正常一轮那样先流式吐字）。
> 前端对这条路径的处理是「流式缓冲为空时退回 `payload.text`」，所以那句话仍然能显示。

界面上：

- 气泡显示一句重连台词（如「信号有点差…我重连一下。」），约 0.9 秒后回到待机。
- 恢复后**新增一条 pet 消息：「会话已恢复，可以继续。」**，并触发朗读（若「🔊 自动朗读」开着）。
- **已有的历史消息不会被重新插入** —— 消息列表**只增加这 1 条**，不会把之前的对话再显示一遍。
- 事件日志确实多了 3 条。

### 为什么算通过

**§16.4 验收项「断线重连不重复展示」**。判据是「重连**不能把已经展示过的内容再展示一遍**」，
可量化的走法：

1. 用两个不同的问题各走一轮 `正常回复`，记下消息列表的条数与内容；
2. 点一次 `重连`，等回到待机；
3. 检查：**历史内容没有任何一条被重复插入**，列表只是末尾多了 1 条恢复提示。

更贴近真实断线的走法：走完一轮 → 点 `重连` → 再走一轮 `正常回复`，
此时**只应新增 1 条 pet 回复**（加 1 条恢复提示），旧内容不得重复出现。

### ✅ 这条验收项现在**技术上成立**了

早期版本这条是**做不到**的：`RuntimeEvent` 里没有 `sequence` 字段，
前端无法判断重连后补发的是不是自己已经渲染过的事件 —— 当时只能靠「Mock 重连时不补发历史事件」
把这个事实绕过去（也就是说，那条验收项目测通过，但一接真后端就会失效）。

现在的实现：

| 机制 | 位置 | 作用 |
| --- | --- | --- |
| `event_id` 去重 | `App.jsx` 的 `seenIdsRef`（Set，>400 条清空） | 同一个事件被原样重发，直接丢 |
| `sequence` 去重 | `App.jsx` 的 `lastSeqRef`（`{session_id: 已处理最大序号}`） | 序号不前进的补发事件，直接丢 |

**两张网都留着**，因为真后端可能只保证其中之一。

### 已知偏差（重要）

- **连点 N 次 `重连`，会得到 N 条一模一样的「会话已恢复，可以继续。」并朗读 N 次** ——
  每次重连各产生一条恢复提示，界面上看起来像在刷屏。
  ⚠️ 但这**不是**去重失效：Mock 每次重连都产生**新的 `event_id` 与新的 `sequence`**，
  从契约角度看它们是三条全新的事件，去重网没有理由拦。**去重针对的是「后端重发同一条事件」，
  不是「用户重复触发」。** 演示时要跟评审说清楚这个区别。
- `resumed_from` 传的是**当前会话自己**（语义上等于"从我这里恢复"），没有旧会话可指。
- ⚠️ 这条路径下三条事件的 `trace_id` **全是 `null`**（上一轮结束时 `traceId` 已被清空，
  重连时没有新开 trace），所以这一段无法归入任何一条可回放的轨迹。
- ✅ 早期版本这里有一个更严重的问题：前端只用自己的流式缓冲（重连路径下它是空字符串），
  所以那句话**永远不显示**，点完「重连」什么都不会出现（不是"不重复展示"，是**不展示**）。
  现在改成了「缓冲为空时退回 `payload.text`」。演示时若仍然"什么都没出现"，
  多半是跑到了 `out/` 里的旧产物 —— 先 `npm run build` 再 `npm run start`
  （或直接用 `npm run dev`，见 `启动说明.md`）。

## 场景 4：渲染进程读不到模型密钥（安全验收）

### 怎么复现

**(a) 静态核对（本次实际执行过，不需要启动应用）**

```bat
cd /d C:\Users\87092\Desktop\deepprof\desktop

:: 1. 源码里没有任何密钥/令牌字样 —— 预期：无匹配
findstr /s /i /r "api_key apikey secret token password bearer" src\*.js src\*.jsx

:: 2. 渲染进程能用什么，全在这一个文件里 —— 预期：只有白名单成员
type src\preload\index.js
```

代码层面的三条结构性证据：

1. `src/preload/index.js` 只 `exposeInMainWorld` 一个对象，共 **18 个成员**
   （3 条会话 + `win` 下 11 个 + `tts` 下 2 个 + 2 个订阅函数），
   **没有** `invoke(channel, ...)` 这类通用通道；
2. 创建窗口时 `contextIsolation: true`、`nodeIntegration: false`，
   `preload` 指向固定文件 —— 渲染进程**没有 Node 环境**；
3. 事件来源只有一条 `runtime:event` 推送通道，方向是主进程 → 渲染进程。

**(b) 运行时核对（DevTools 控制台）**

在渲染进程控制台执行下面几行，逐条看结果：

```js
typeof window.require              // 期望 "undefined"
typeof window.process              // 期望 "undefined"
typeof window.ipcRenderer          // 期望 "undefined"
Object.keys(window.deepprof)       // 期望 8 个：
                                   //   ["sendMessage","cancel","reconnect","onEvent",
                                   //    "onWalk","tts","exportPreference","win"]
Object.keys(window.deepprof.win)   // 期望 11 个：setIgnoreMouse/setHitRegion/setUiOpen/moveBy/
                                   //           dragState/setChatOpen/setRoaming/wander/home/
                                   //           setAlwaysOnTop/quit
Object.keys(window.deepprof.tts)   // 期望 2 个：synthesize/selftest
typeof window.deepprof.invoke      // 期望 "undefined"
```

打开 DevTools 的方式：本项目没有禁用 Electron 的默认应用菜单，`Ctrl+Shift+I` 一般可用；
若快捷键无效，可在主进程临时加一行 `win.webContents.openDevTools()`（属代码改动，**本轮未做**）。

> ⚠️ **诚实标注**：本次交付**只执行了 (a) 的静态核对**。
> 写文档期间 `src/main/index.js` 与 `src/renderer/src/App.jsx` 正被其他人修改，
> 为避免与改动冲突、也避免弹出窗口干扰，**没有实际启动应用去跑 (b)**。
> (b) 的指令留作验收时现场执行。

### 预期现象

- (a) 第一步无匹配；(b) 的 `typeof` 全部为 `"undefined"`。
- `window.deepprof` 只暴露上面 **19 个可调用成员**（8 个顶层键，其中 `exportPreference` 最容易被漏数）；
  渲染进程**无法**指定 provider / model，只能通过 `sendMessage` 请求"走一轮"。

### 为什么算通过

§16.4 验收项「渲染进程不持有模型密钥」。**判据不是"界面上看不到密钥"，而是这四条同时成立**：

1. 渲染进程没有 Node 能力（`require` / `process` 拿不到）；
2. preload 只暴露白名单，没有通用 IPC 入口；
3. 全项目源码里不存在密钥字段（`grep` 无匹配）；
4. 结构上，将来真实模型调用只发生在主进程，渲染进程永远只能发 `session:send`。

任何一条不成立都不能算通过 —— 尤其是第 2 条：只要暴露了任意通道名的 `invoke`，
白名单就形同虚设。

### 已知偏差

- 当前还没有真实模型调用，所以这条验收项现在是**结构上成立**（不是"实测通过"）。
  接真实 Provider 后需要重测一遍，届时仍应满足上面四条。
- `sandbox: false`（为了让 preload 能 `require('electron')`）。这会在 preload 层引入
  Node 能力，是本项目为兼容性做的取舍 —— **不在 preload 里做任何凭据相关的事**是前提。
- ✅ **TTS 这条链路需要注意**：现在语音合成**主进程会起一个 `python` 子进程**
  （`tools/tts/say.py`）并读写临时文件。渲染进程拿到的只是 `data:audio/mpeg;base64,...`，
  **碰不到文件系统、也没有任何凭据**。但接真实云端 TTS 时，
  密钥仍必须留在主进程 —— 这条边界不能因为「反正只是个语音」而放松。

## 场景 5：加载中卡住（只有请求、没有响应）

### 怎么复现

点 **`加载中`** 按钮。

### 预期现象

事件序列到 `model.requested` 就**停住了**：

```text
session.started / agent.turn.started / pedagogy.node.entered {node:"Assess"}
── 约 300ms ──
model.requested {provider, model}
（之后没有任何事件）
```

- 气泡一直显示一句 loading 台词 + 三个跳动小点，**不超时、不报错、不自动恢复**。
- `取消` 按钮**一直可见**（这是刻意保留的出口）。
- 动画是 `think`（慢慢左右轻晃）。

### 为什么算通过

这是刻意构造的"最坏情况"：**只有请求、永远没有响应**。验证三件事：

1. **不崩**：界面不卡死、动画继续跑、窗口仍可拖动/穿透；
2. **不误报成功**：没有 `model.completed` 就绝不会把空字符串当成一次回答入库，也不会朗读；
3. **留了出口**：点 `取消` 能立刻回到「已取消」（即场景 2-B），不需要重启应用。

第 3 条是这个场景真正的通过判据 —— 卡住不可怕，**卡住之后出不来才可怕**。

### 已知偏差

- Mock **没有超时机制**，所以这个状态会一直持续。真实链路按 §7.3 应该有超时与回退，
  这部分未实现。
- 当前也没有"正在重试"之类的中间提示，用户无法区分"在慢慢算"和"已经死了"。

## 场景 6（新增）：装配/绑定失败的空回复 —— **前端无法区分**

> ⚠️ **本场景当前在界面上不可复现**，写在这里是因为它是 v0.4.1 新引入的一类失败，
> 而且**桌宠侧完全没有处理**。接真后端后它会自然出现。

### 背景（v0.4.1 §7.3 新增）

v0.4.1 要求「装配与绑定失败必须显式」，四种情况都要返回结构化状态，
**不允许静默兜底成一段自由发挥的文本**：

| 情况 | status |
| --- | --- |
| 组合根漏装配 | `no_binding` |
| 绑定写错能力名 | `capability_not_found` |
| 绑定引用了请求里不存在的字段 | `invalid_request` |
| 选不到模板 / 兜底模板缺失 | `error(template_not_found)` |

而且明确了一条产品取舍：

> 失败的学生可见表现因此是"**空回复**"，这是有意的取舍：
> **装配错误是部署缺陷，应当响亮地暴露，而不是用一句安慰话遮住**。

### 桌宠侧的问题

`CapabilityResult`（含 `status` 六态）是 `RuntimePort.execute` 的返回值，
**在「图 ↔ Runtime」之间传递，不走事件流**。事件流里**没有任何字段承载 `status`**。

所以桌宠收到一个 `content` 为空的轮次时，**无法区分**：

| 情况 | 按 §7.3 意图应有的表现 | 桌宠实际的表现 |
| --- | --- | --- |
| 装配失败（`no_binding` / `capability_not_found` / …） | 「响亮地暴露」 | **什么都不说**（和下面一样） |
| 模型真的没话说（正常的空 content） | 保持沉默 | 什么都不说 |

这与 §7.3「响亮地暴露」的意图**在表现层是矛盾的** —— 桌宠把「部署缺陷」和「正常的沉默」
渲染成了同一个画面。

### 为什么算通过（接真后端后的验收判据）

1. 后端确实按 §7.3 返回了结构化 status（可在后端日志或 `/health` 的 `action_bindings` 看到）；
2. **前端能被明确告知**这个 status（当前做不到 —— 建议写进 `pedagogy.decision.capability_status`）；
3. 团队对「装配失败时桌宠该不该说点什么」有明确决策并落地。

### 已知偏差

- 前端侧**完全未实现**，因为契约里还没有字段可读。
- 需要一次团队决策：装配失败时桌宠应该说「我这边配置有点问题」还是保持沉默？
  §7.3 的字面意图倾向于前者，但那需要一个新的学生可见表述，
  而 §16.4 的表现层目前没有这个概念。见 `INCONSISTENCIES.md` 第 25 条。

## 附录 A：界面**无法**复现的三个失败样例

这三条在当前界面上没有入口，写在这里是为了让联调时知道**该看什么**。
不要为了演示而在文档里假装它们能点出来。

### A-1 网络错误（`reason:'network'`）

- **为什么点不到**：`run(text, 'reconnect')` 这条分支（发 `model.failed{CONN_RESET}` +
  `agent.failed{reason:'network'}`）**没有被任何按钮调用**。界面上的 `重连` 按钮走的是
  另一条通道 `session:reconnect`（即 `reconnect()`），产出的是 `session.resumed`。
  要从渲染进程调 `window.deepprof.sendMessage(文本,'reconnect')` 才能触发。
- **若触发的预期现象**：与场景 1 同一条链路，只是文案换成
  `模型失败：连接中断` + `本轮失败：network`。
- **它的价值**：暴露了一个入口缺口 —— 契约里定义了 network 失败，UI 却没有演示入口。
- **状态**：⚠️ 未实测。

### A-2 未知教学节点静默失败（机制仍在；**PNG 动画表已补 Reflect，另外一处仍有缺口**）

- **为什么点不到**：Mock 从不发 `Reflect` 或 `Test`（只走 Assess→Teach→Ask→Hint→Correct→UpdateProfile
  这 6 个）。复现需要后端发一个节点名。
- **预期现象**：若节点名**不在** `NODE_TO_ANIMATION` 里，桌宠**不报错、不掉帧、不卡顿**，
  默默回到待机姿势 —— 因为解析函数末尾的 `|| 'idle'` 兜底生效了。而"待机"正好也是
  没有教学节点时的**正常**表现，所以**从现象上完全看不出这是 bug**。
- **为什么把它算作失败样例**：它示范了本模块最危险的一类故障 —— **静默失败**。
  验收时后端发得对、前端也没崩，只有逐帧盯着小人看才会发现该节点没有任何专属表现。
  对后端的直接要求是：**新增节点名前必须通知前端同步补映射，不能指望测试暴露问题。**

**✅ 已补的部分**：

| 表 | 是否有 Reflect | 生效范围 |
| --- | --- | --- |
| `NODE_TO_ANIMATION`（`petAnimations.js`） | ✅ 有（→ `think`） | **默认的逐帧模式**，所以正常演示不受影响 |
| `NODE_TO_EXPRESSION`（`petState.js`） | ❌ 无 | 死代码，不影响画面 |
| `NODE_TO_LIVE2D`（`petState.js`） | ❌ 无 | **Live2D 模式**下会退化成默认待机 |

**这一轮复核新发现的两个静默失败（1 已修复、1 仍在）**：

1. **~~`RigPet` 没有 `case 'correct'`~~** —— ✅ **已修复（核对于 2026-09-19）**：
   `RigPet.jsx` 现在是 `case 'correct':`（带一段注释说明这个坑）。**下面保留修复前的记录**，
   因为「补了映射表、忘了补播放器 case」这类静默失败以后还会以别的名字出现：
   当时 `NODE_TO_ANIMATION.Correct = 'correct'`，但 `RigPet.jsx` 的 `switch` 分支只有
   `walk / talk / teach / ask / hint / think / sad / quiz / happy`，
   落到 `default`（idle 呼吸）。**逐帧模式正常（有 `correct.png`），分层模式静默退化。**
   复现（修复前）：右键菜单点「换成分层走路」→ 走一轮 → 在 Correct 节点看小人（无任何反应）。
2. **`NODE_TO_LIVE2D` 缺 `Reflect`** —— 🔴 **仍在**（`petState.js` 的 `NODE_TO_LIVE2D` 只有 7 个键，没有 `Reflect`）。
   切到 Live2D 后，后端发 Reflect 会落到
   `{motion:'Idle', motionIndex:0, expression:0}`（一个无表情的待机）。

**核对方法（不改代码）**：把后端实际发出的节点名集合，
与 `petAnimations.js` 的 `NODE_TO_ANIMATION` **和** `RigPet.jsx` 的 `case` 集合
**三者分别对照** —— 任何一处的差集都是会被静默吞掉的那些。
这一轮的问题正是「补了映射表，忘了补播放器的 case」。

### A-3 装配/绑定失败的空回复

见场景 6。同样**界面不可复现**（当前 Mock 不会产生这种结果），
且前端连「判断它发生了」的能力都还没有。
