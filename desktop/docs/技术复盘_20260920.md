## 一、通用教训（**先读这个**）

### 1.1 这个项目最大的敌人是「静默失败」

不报错、不崩溃、退出码 0、日志看着正常，**只是表现不对**。
本轮 13 个坑里，**10 个属于这一类**（坑 2、3、4、5、7、8、9、11、12、13）。
它们的共同结构是：

```
某一步 quietly 没生效  →  下游拿着错的数据继续跑  →  最终表现不对，但没人知道是哪一步
```

**为什么这类 bug 在这个项目里特别多**：因为这条链路是
`AI 出图 → Python 图像流水线 → PNG 资产 → React/PixiJS 播放 → Electron 打包 → exe`
——**六段里没有一段有类型检查**。图像是"能看就行"的东西，
一个 `if` 写错不会抛异常，只会让**几万个像素里的一小撮**不对。

**唯一有效对策**：每一段都设计一个**能自动判死**的量化判据，并且**判据本身也要被怀疑**
（见 1.2）。本轮的正面例子是"轮廓宽高比 0.77"和"轮廓 IoU = 1.000000"——
它们能把"肉眼看差不多"变成"数字对不上就是错"。

### 1.2 度量要设计成「能证伪」的

判据选错，不是"测不出来"，是**会让你得到相反的结论，而且你还很自信**。
本轮在这上面栽了两次（坑 3、坑 4），上一轮（09-20 傍晚）也栽过一次。

判断一个判据好不好，问三个问题：

1. **它测的那个量，和"我要找的事件"是单调相关的吗？**
   ❌ "与中位帧的整体差异" —— 呼吸缩放让**整幅图**都在动，差异比闭眼**还大**。
   ✅ "蓝眼珠像素数" —— 闭眼时它**必然**掉，别的因素动不了它。
2. **被测信号在总信号里占多少？**（信噪比）
   ❌ 把检测区域取到包含蓝蝴蝶结 —— 真实跌幅被稀释到 **16%**，阈值却定成 60%，一帧都抓不到。
   ✅ 区域只框住眼睛。
3. **阈值是"绝对值"还是"相对值"？相对谁？**
   相对值更稳，但**中位数会被污染**（坑 4 就是"中位"本身不对）。

### 1.3 验证有三层，一层比一层贵

```
① 构建通过      —— 最便宜，也最不值钱（本轮 0.2.1 构建成功 ≠ 显示的是新素材）
② 跑起来        —— 比 ① 强，但可能跑的是"旧进程/旧包/旧状态"
③ 跑起来 + 用对方法 —— 才算数（CDP 驱动 + screencast 采样 + 干净进程 + 判据正确）
```

**本轮第 ③ 层真的把结论翻过来一次**：截图连拍 100 张全是睁眼，结论"没在眨眼"是**错的**；
换成 screencast 后 25 秒抓到 **4 次眨眼**，每次 **10~11 帧 ≈ 110ms**。

### 1.4 量化结果和肉眼矛盾时，**两个都要怀疑**

坑 2 就是这个形状：**"绿色像素已清零"的计数是对的，肉眼却还看得见一道青绿月牙**。
这时候**不能**二选一——正确的动作是**去找第三个判据**（换成 `b - g`），
因为"计数对 + 肉眼可见"本身说明**两个判据量的不是同一个东西**。

## 二、用到的技术（原理逐条）

### 2.1 素材归一化流水线 —— 四件事，各自防一种翻车

`desktop/tools/素材流水线/归一化帧.py`（权威副本在 `_素材工作区/`，见坑 12）。
脚本头部的注释（`归一化帧.py:10~30`）已经把四条写清楚了，这里补**它们各自防什么**：

| # | 做什么 | 不这么做会怎样 | 代码位置 |
| --- | --- | --- | --- |
| 1 | **连通域去背景**：只有**和画布边缘连通**的浅色区才算背景 | 用"按颜色抠浅色"的话，**白衬衫、白袜子会被抠穿**（头发之间、腿之间的白色区域和背景同色，但不与边缘连通） | `strip_background()`，`归一化帧.py:120` |
| 2 | **整批共用一个缩放系数** | 逐帧缩放"到同一高度"会把**走路时的上下起伏抹平**，人变成纸片 | `逐帧` 模式，`归一化帧.py:389` 附近 |
| 3 | **按头部中心对齐**，不是外接框中心 | 走路时**腿在伸**，外接框一直在变；按它对齐会**左右抖** | `HEAD_FRAC = 0.30`，`归一化帧.py:79`；量测在 `measure()`，`:262` |
| 4 | **脚底对齐同一基线** | 每帧脚的高度不一样，走路会"踩空" | 同上，`normalize_action()`，`:337` |

**两种模式**（`--模式 {表情,逐帧}`，`归一化帧.py:576`）：

- **`逐帧`**（走路 / 待机 / 眨眼 / 说话）：整批**共用同一个**系数 → 保住动作起伏。
- **`表情`**（9 张立绘）：**逐张**缩放到同高 → 否则切表情时角色会**忽大忽小**。

> ⚠️ **模式选错本身就是静默失败**：用 `表情` 模式跑走路，得到的是一组"高度完美但起伏被抹平"的帧，
> 脚本不会报错，肉眼看单帧也看不出来 —— 只有**播起来**才知道人变成纸片了。

> 📌 **还有一道前置工序**：`对帧.py`。即梦出图时**画布尺寸会飘**（idle 是 1728×2304 竖幅、
> 眨眼帧却是 2048×2048 方图），角色在画布里的**相对大小**也跟着变 24%。
> `归一化帧.py` 的逐帧模式有一条**阻尼校正**（`DAMP=0.7`，本来是给走路的"一胀一缩"设计的），
> 它会把 10.5% 的真实尺寸差**压成 3.2%** —— **压住不等于消除**，眨眼时脸还是会缩一下。
> **阻尼是给"动作起伏"用的，不该拿来兜"出图画小了"**。正确做法是先用 `对帧.py` 把各帧
> 缩放到基准帧一样大，再进流水线，这样阻尼系数天然接近 1。

### 2.2 局部区域移植合成 —— **本轮最值得学的一招**

`desktop/tools/素材流水线/眨眼合成.py`。问题：AI 给的"睁眼""闭眼"是**两次独立生成**。

实测的三个数（`眨眼合成.py:6~11`）：

- 全身 **21.5%** 的像素不同
- **整体平移解释不了** —— 挪 4px 只消掉 14% 的差异
- 轮廓框底部差 **9px**

→ 所以**整图硬切会全身抖一下**。那不是眨眼，是"整个人抖了一下"，
因为头发丝、裙褶、描边、脚**全都在动**。

**解法**：`blink_1 = 睁眼图(身体) + 闭眼图的眼部矩形(局部平移配准后贴上)`。

```
find_eyes()    靠【深色睫毛线】定位眼部，范围卡死    眨眼合成.py:80
best_offset()  在脸部窗口内搜最佳平移，让 B 对齐 A   眨眼合成.py:92
feather_mask() 眼部矩形羽化（约 499×225，宽而扁）    :110
```

结果：**合成后两帧的轮廓 IoU = 1.000000**，身体像素与基准完全一致 → **抖动为零**。

> 🎓 **为什么这一招值得学**：它把"两次独立生成的图能不能混用"从一个**玄学问题**
> 变成了一个**工程问题** —— 不是"祈祷 AI 出得一样"，而是
> **只在必须变的地方变，其余地方直接复用基准图的像素**。
> 这个思路可以推广到任何"两个版本应该只差一点点"的合成场景（说话嘴部、表情微调……）。

> ⚠️ **`feather_mask()` 有个抄反必炸的细节**（`:110~115`）：眼部矩形是**宽而扁**的（499×225），
> 羽化如果按"四边各缩 pad"写反了方向，会把整张图抹掉。**宽扁矩形是"反直觉"的那一类**，
> 写这类几何代码要拿具体的数验一遍。

### 2.3 连通域 + 形态学拆图

`desktop/tools/素材流水线/三格表情拆分.py`。把"三格参考图"拆成三张独立立绘，
去掉**底部英文标签牌**和**头旁的语义气泡**。

```python
PANELS      = [("hint", 0, 651), ("correct", 651, 1337), ("quiz", 1337, None)]   # :58
find_label_cut()  找"脚底"与"标签牌"之间的空行带，返回切在哪                      # :91
keep_body()       只留【含鞋底的那一块】连通域                                  # :140
```

**为什么用"含鞋底的那一块"而不是"最大的那一块"**（`:144`）：
**最大的块未必是角色**（气泡偶尔比瘦小的角色还大），但**鞋底一定是角色**，脚在画面最下方。

> 📌 **验收判据是轮廓宽高比，不是肉眼**：脚本会把"角色框宽高比"打出来，
> 和站姿基准 **0.769** 比（`ASPECT_WARN`，`:69`）。
> **气泡只要残留一点，宽高比就会往上跳** —— 判据比肉眼灵敏，而且不吵架。

### 2.4 颜色判据的设计 —— 判据要按「要区分的那两类东西的差异」来设计

同一个文件，`bubble_tint_mask()`（`:117`），最终判据在 `:137`：

```python
return (g > r + 15) & (b - g < 40)
```

**为什么不能只靠前两项。** 见坑 2，那里完整记了返工过程。这里只留结论：

| 物体 | 实测 RGB | `b - g` |
| --- | --- | --- |
| 角色的蓝丝带 | `(90, 163, 237)` | **74**（蓝远压过绿） |
| 气泡描边的**抗锯齿外缘**（青绿） | `(112, 174, 189)` | **15**（绿蓝相当） |

→ **真正的分界是 `b - g`**。`g > b` 这类"我以为的判据"**恰好把这两类一起放过**。

> ⚠️ 调用处**只在气泡周边那一圈**应用（`三格表情拆分.py:210`），**不全身撒网** ——
> 这样换了有绿色的角色也不会误伤。**判据的适用范围要跟着它的假设走**：
> 这个判据隐含"角色的配色不含绿"，所以它只该用在该假设立得住的地方。

### 2.5 CDP（Chrome DevTools Protocol）程序化驱动桌宠做实测

`desktop/tools/实拍驱动.mjs`。**为什么必须走 CDP**：
桌宠是**置顶透明窗口**，从外面点鼠标要**赌坐标** —— **DPI 一缩放就全错**。

走 CDP 可以直接在页面里 `element.click()` / `dispatchEvent`：

```js
el.dispatchEvent(new MouseEvent('dblclick', { bubbles: true, cancelable: true, view: window }))
```

**为什么这样能触发 React 的 onClick / onDoubleClick**：
**React 的事件不是挂在元素上的，是挂在 root 容器上统一委托的**。
原生事件从目标元素**冒泡上去**，照样被 root 的监听器收到，再派发给对应的组件。
所以只要 `bubbles: true`，程序化合成的事件和真人点击**走的是同一条路径**。

**高频采样用 `Page.startScreencast`**（`实拍驱动.mjs:198`）：

- 它是**每绘制一帧推一张**（推模式），**没有轮询往返延迟**，实测约 **100fps**。
- 对比 `Page.captureScreenshot`：一次往返 **200ms+**，抓 110ms 的闭眼会**直接从上面跨过去**。

### 2.6 Win32 `WindowFromPoint` 验证点击穿透

**想知道"这个点到底归哪个窗口"，不要靠猜、不要靠肉眼看桌面** —— 直接问系统：

```c
HWND h = WindowFromPoint(pt);
DWORD pid; GetWindowThreadProcessId(h, &pid);
```

返回的 PID 是不是桌宠的进程 —— **一目了然，而且可以写进断言**。

> 🎓 **这条不止用于点击穿透，它是一种通用姿态**：
> 凡是"我觉得这个操作应该落到 X 上"的判断，**都去找一个能直接提问的系统 API**，
> 而不是靠观察现象反推。反推出来的结论**没有失败模式**，也就**无法证伪**。

> 📌 背景：动态点击穿透由主进程统一决策（`src/main/index.js:619` 起，`win.setIgnoreMouseEvents(ignore, { forward: true })`，
> `:673`）。原先渲染进程自己调，出过"点空白处穿透失效"和"角色点不动"两个问题。

### 2.7 幂等性验证（md5）

改完流水线脚本后，**用 md5 比对确认重新跑一遍输出逐字节不变** ——
证明改动**没有副作用**。这是"改动很大但输出应该不变"时**最便宜的免疫检查**。

## 三、踩过的坑（13 条）

> 每条格式：**现象 → 为什么 → 怎么发现的 → 教训**。
> 保留"当初怎么想错了"的痕迹 —— 那才是复盘的价值。

### 坑 1 · 气泡不是"拖一条细颈"，是"贴着头发"

- **现象**：想用形态学**开运算**去掉头旁的语义气泡 —— 腐蚀把细颈断开 → 气泡变成独立连通域 → 只留角色主体。
- **为什么错**：气泡**和头发是大面积贴住的**，根本没有"细颈"可断。腐蚀到 **14px 都断不开**。
  更糟的是腐蚀-膨胀的**重建会顺着连接处原路长回气泡里去**，等于白做。
- **怎么发现的**：放大到 **4 倍**、打 **20px 网格**看才看明白是"贴着"而不是"连着一条线"。
  调试图落在 `动作帧/预览/_诊断_*_气泡区.png`。
- **教训**：**形态学参数调不动的时候，先去看图，不要继续加大参数。**
  "腐蚀不掉"本身就是个信号：**你假设的拓扑结构可能是错的**。
  另外**留一张"量出来的"矩形**（`三格表情拆分.py:64` 的 `BUBBLE_RECT`），
  注释里写明**换图必须重新量** —— 因为它是"量出来的"不是"算出来的"。

### 坑 2 · 颜色判据 `g > b` 恰好放过了要抓的东西（**这条最值得记**）

- **现象**：绿色气泡的**抗锯齿外缘是青绿色**（teal），实测 `rgb = (112, 174, 189)`。
  判据写的是"`g` 明显大于 `b`"，于是**恰好把蓝白色的角色和这道青绿边一起放过**。
  结果：**"绿色像素已清零"的计数是对的，肉眼却还看得见一道绿色月牙**。
- **为什么**：`(112,174,189)` 里 `g=174`、`b=189` —— **`b` 比 `g` 还高**，
  "g 明显大于 b"这个条件**压根不成立**，所以它被判成"不是绿"，留着。
- **怎么发现的**：**计数说清零、肉眼说还在** —— 两个判据打架，于是不再二选一，
  去把那个像素**打出来看**，量到了 `(112,174,189)`。
- **正解**：真正的分界是 **`b - g`**：
  角色的蓝（丝带）`(90,163,237)` → `b-g = 74`；气泡青绿 `(112,174,189)` → `b-g = 15`。
  判据要写成「**`g` 明显高于 `r`（是绿系）且 `b` 不比 `g` 高多少（是青绿不是纯蓝）**」。
- **教训（本轮最重要的一句话）**：
  **判据要按"要区分的那两类东西的差异"来设计，不能按"我以为的样子"来设计。**
  设计完要**回头拿两类真实的样本各验一个**，而不是验完"要抓的那类"就收工。

### 坑 3 · 截图连拍抓不到 110ms 的眨眼，得出的是**相反的结论**

- **现象**：连拍 100 张全是睁眼 → 结论"没在眨眼"。
- **为什么**：闭眼只保持 **110ms**，而 `Page.captureScreenshot` 一次往返要 **200ms+** ——
  **会直接从上面跨过去**。
- **怎么发现的**：不信"功能是好的但测不到"，回头算了一下采样率 vs 事件持续时间。
- **正解**：换成 `Page.startScreencast`（约 100fps，推模式无轮询延迟）后，
  **25 秒抓到 4 次眨眼、每次 10~11 帧**。
- **教训**：**采样率低于被测事件的持续时间时，测不到 ≠ 不存在。**
  这句话要贴在显示器上 —— 它会以很多种面貌出现（截屏、日志采样、轮询、心跳）。

### 坑 4 · 指标选错会得出完全相反的结论（**本轮犯了两次**）

- **第一次**：用"与**中位帧的整体差异**"找眨眼 → 挑出来的其实是 **1px 的呼吸缩放（bob）**，
  它的差异（**5.9**）比闭眼（**0.8**）**还大** —— 因为整幅图都在动，每条描边都在变。
  → **真正要找的信号，比噪声还小。**
- **第二次**：改用"数**蓝色像素**"（对的方向），但**把区域取大了** ——
  **被蓝蝴蝶结占了大半**，真实跌幅只有 **16%**。阈值却定成"中位的 **60%**" → **又是一帧都没抓到**。
- **怎么发现的两次都是同一个办法**：**判据和肉眼打架时，不挑一个信，去查第三个量**。
- **正解**：区域只框住眼睛 + 阈值按**实测跌幅**定，而不是拍脑袋。
  最终测到 t38 / t86 两次闭眼、**间隔 5.76 秒**。
- **教训**：同坑 3 —— 而且这条在 **09-19 就栽过一次**（见 `_文档/DeepProf_复盘_2026-09-19.md`）。
  **同一个错误连着栽三次，说明它不是"疏忽"，是"缺流程"。** 见 §四。

### 坑 5 · 状态残留：**测了个寂寞**

- **现象**：连拍一堆帧，一帧都没眨眼。
- **为什么**：眨眼 overlay 只在 `animName === 'idle'` 时才挂（`App.jsx:684`），
  而点过教学节点 / 跑过一轮 Mock 之后 `node` 或 `status` 还留着，
  小人显示的是 `sad` / `teach` —— **那种状态下根本不会眨眼**。
- **怎么发现的**：先怀疑判据（上面两条），判据修对了还是抓不到，
  才回头看**被测对象当前处于什么状态**。
- **教训**：**测试要从"已知的干净初始状态"开始**，而不是"接着刚才那轮继续"。
  要么先跑一次 `收尾` 清节点，要么**重启一个干净进程**。

### 坑 6 · `Page.reload` 复位反而更糟

- **现象**：想用重载页面来复位状态。
- **为什么**：重载之后**透明窗口的背景变成不透明黑**、窗口尺寸也变，帧间乱跳 —— **比不复位还糟**。
- **教训**：**"复位"这个动作本身就可能有副作用**，尤其在 Electron 这种
  "页面 + 原生窗口"两层状态的地方 —— **`reload` 只重置了上面那层**。
  正确做法是**重启一个干净进程**（贵，但确定）。

### 坑 7 · 窗口不在前台时 Electron 会**节流重绘**

- **现象**：连拍回去一大堆**逐像素完全相同**的帧。
- **为什么**：窗口不在前台 → Electron 节流重绘 → 页面根本不重绘。
- **怎么发现的**：发现"帧完全相同"这个**不自然的整齐**（真实动画不可能一模一样）。
- **教训**：**每个模式都得先 `Page.bringToFront`**（`实拍驱动.mjs:186` / `:230`）。
  更一般地：**"完全相同的连续采样"是个危险信号**，它通常意味着**采样端或被测端有一边停了**，
  而不是"这段时间真的没动"。

### 坑 8 · 改完素材 ≠ 重打包（**交付环节最容易漏**）

- **现象**：`release/` 里的 exe 打于 **17:23**，而这一轮素材 **18:47** 才进工程 ——
  **组长双击会看到旧形象**（张嘴待机 + 复用表情）。
- **为什么**：`assets/pet/` 是**被 exe 打包进去的**，改素材不会自动重打；
  而且 `release/` 是 **gitignore** 的，**exe 不随分支走**，只能走 GitHub Release。
- **怎么发现的**：**对比了两个 mtime**（exe 的 vs 素材的）—— 这一步现在应该变成习惯动作。
- **处置**：版本 **0.2.0 → 0.2.1**（避免 Release 附件重名 **422**）→
  `NODE_OPTIONS=--use-system-ca npm run dist` 重打（**19:11**）→
  **把打出来的 `release/win-unpacked/DeepProf桌宠.exe` 真跑一遍、CDP 截图确认显示的是新待机**。
- **教训**：**动完 `assets/pet/` 就要问一句"包要不要重打"**。
  ⚠️ **这个坑上一轮刚踩过**（09-20 傍晚那次："旧包是换角色之前打的"）
  —— **会反复踩，所以它必须是清单上的一行，不能靠记性**（见 §四）。

### 坑 9 · 警告判据用错了统计量，漏报了一次真实的放大

- **现象**：三张新表情被放大 **1.87~1.90 倍**、图会糊，但脚本**一声没响**。
- **为什么**：放大警告写的是 `min(scales) > 1.02`（`归一化帧.py` 旧版）。
  **表情模式是逐张各一个系数** —— 同批只要有一张是缩小的，
  最小值就被它压下去，**整批在放大也不报警**。
  实测：同批的 `think.png` 系数是 **0.987**，于是三张 1.9× 的放大被它盖住。
- **怎么发现的**：肉眼看新表情"有点糊"，回头读脚本才发现判据写的是 `min`。
- **正解**：改成**逐张数有几张在放大** —— `over = [s for s in scales if s > 1.02]`
  （`归一化帧.py:439`），并打印"最小的原图角色只有 Xpx 高"。
- **教训**：**`min`/`max`/`mean` 这类聚合，隐含一个"整批同质"的假设。**
  一旦模式变成"逐张各一个参数"，聚合量就**不再是那个意思了**。
  **判据和它依赖的假设，要写在同一个地方**（现在注释就贴在 `:433` —— 正确做法）。

### 坑 10 · 脚本缺一句 utf-8 重配置，在 GBK 控制台下**必崩**

- **现象**：`眨眼合成.py` 要打印 `⚠️`（U+26A0），GBK 编不出来 → `UnicodeEncodeError`。
  **按文档原样跑就是直接失败。**
- **为什么**：Windows 控制台默认 **GBK**。姊妹脚本 `归一化帧.py` 一直有那句
  `sys.stdout.reconfigure(encoding="utf-8")`（`:41`），这个漏了。
- **为什么一直没人发现**：**崩点在存盘之前，所以不留半个残文件** —— 没有痕迹。
  加上这个脚本当时在 `_素材工作区/`（git 排除），**不在任何人的视野里**。
- **教训**：**"没留残文件"不等于"没出过事"**。也说明
  **同一个模板复制出来的一组脚本，要有一个地方统一保证"该有的都有"**（现在都补上了：
  `眨眼合成.py:64`、`三格表情拆分.py:50`）。

### 坑 11 · 脚本按 `__file__` 找数据根 → 从 `tools/` 跑会**静默失败**

- **现象**：从 `desktop/tools/素材流水线/` 下跑，只打印一句「原始目录是空的」就退出，
  **退出码还是 0**。
- **为什么**：脚本用 `HERE = os.path.dirname(os.path.abspath(__file__))` 定位 `动作帧/`
  （`归一化帧.py:45~46`），而真正的数据在 `_素材工作区/动作帧/`。
  从 `tools/` 那份跑，它会去找 `tools/素材流水线/动作帧/原始/` —— **那个目录不存在**。
- **怎么发现的**：**输出里那句"原始目录是空的"，配合退出码 0** ——
  等于"什么都没干，但告诉调用方成功了"。
- **教训**：
  1. **`__file__` 相对路径是"看你在哪跑"的**，对**人跑**的脚本可以接受，
     但对**别人按文档跑**的脚本就是地雷 —— 文档写 `cd A && python x.py`，
     而脚本找的是 `B/`，**两边永远不会同时成立**。
  2. **退出码 0 是"成功"的承诺** —— 什么都没做就返回 0，是**最恶劣的一类静默失败**。
  3. 治本方案是**按环境变量或参数找数据根**（`tools/README.md` 已记），
     **本轮没做**（怕动到别的动作）—— 所以坑还在，只是被写下来了。

### 坑 12 · 两份脚本副本会**分叉**

- **现象**：`_素材工作区/` 与 `desktop/tools/素材流水线/` 各有一份脚本
  （因为前者被 git 排除、必须留一份能跑的），跑到哪一份**结果不一样**。
- **为什么**：**手工保持两份一致**，而人不会记得。实测 `预览.py` 和 `拆腿.py`
  **已经不一致**了（`tools/` 那份新，`_素材工作区/` 那份还停在 09-19）。
- **教训**：**任何"两份手动同步的副本"都会分叉**，只是时间问题。
  这是**结构性缺陷**，不是纪律问题 —— 所以 `tools/README.md` 里明确写了
  "动手前先 diff 一下"（**止损**），并把治本方案记下来（**没做**）。
  下一个人接手时，**这一条应该是第一个要修的**。

### 坑 13 · ripgrep 默认跳过 git 排除的目录

- **现象**：项目文件夹改名时（大写 `DeepProf` → 小写 `deepprof`，
  09-20 组长要求对齐仓库/模块命名），用 rg 全文扫**旧文件夹名**只找到了 `desktop/` 里的几处，
  **`_素材工作区/` 里 11 个脚本硬编码的绝对路径全漏了** —— **一跑就崩**。
- **为什么**：rg 默认遵守 `.gitignore` **和 `.git/info/exclude`**。
  本项目恰恰是用 `.git/info/exclude` 挡 `_素材工作区/` 的（为了不动组长的 `.gitignore`）。
- **怎么发现的**：**跑的时候崩了**才发现的 —— 属于"用真跑兜住了搜索的漏"。
- **教训**：
  1. **搜索工具默认会"帮你"过滤，而过滤规则来自版本控制配置** ——
     做"全域替换/全域检查"时要知道它在替你做主。
     要覆盖全量得显式 `--no-ignore`（或 `-uu`）。
  2. **被 git 排除的目录 = 双重盲区**：不在 diff 里、不在搜索里、也不在交付里，
     但它**在运行时**（脚本一跑就崩）。
  3. 所以"改名"这类全局操作，**最后一定要有一步"真跑一遍"**，不能只靠静态搜索。

### 4.1 立规矩（写进习惯，不靠记性）

### 4.2 三个"下次一定先做"

1. **先写判据，再动手改。**
   本轮有两次是"改完了才发现测不出来"。**判据是验收标准，不是事后补充**。
2. **判据报警之后，要能定位到"哪一步错了"，而不只是"结果不对"。**
   现在流水线每一步都打日志（`三格表情拆分.py` 会打印连通域数、抹掉多少像素、宽高比），
   这个习惯要**继续**——它是把"静默失败"变成"有声失败"的唯一手段。
3. **任何"两次独立生成"的素材，第一反应是"能不能局部移植"，不是"能不能对齐"。**
   §2.2 那一招改变了问题的性质 —— 值得先想它。
