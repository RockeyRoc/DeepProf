## 1. 先复核「已知的两条」：它们其实不是机器相关的

任务里点名的两条我查了，结论是：**它们不是"换 DPI 就失效"的标定值，根因已经能说清了，而且和机器无关。**

### 1.1 `SCREEN_FACTOR` 的"未查明根因"，就是 geometry.json 与 PNG 分辨率差 2 倍

**在哪**：`desktop\src\renderer\src\FramePet.jsx` 的 `SCREEN_FACTOR` 常量本体，以及 `fit()` 里用它算缩放的三个下限

**根因（这次查到了，是算术上完全吻合的）**：

渲染端算缩放用的是 `FramePet.jsx` 的 `contentSize()`：

```js
return { w: geo.char_x1 - geo.char_x0, h: geo.target_h || geo.char_y1 - geo.char_y0 }
```

它**只信 `geometry.json`，完全不看真实贴图的分辨率**。而：

| 数据 | 值 | 出处 |
| --- | --- | --- |
| 归一化规格声明画布 | 1536×1536、角色高 `target_h`=1200 | `desktop\tools\素材流水线\动作帧\归一化\_规格.json` |
| `expressions/geometry.json` | canvas 1536、char_y 212…1413（高 1201）、target_h 1200 | `desktop\...\assets\pet\expressions\geometry.json` |
| **我 16:52 第一次量到的 `expressions\*.png`** | **768×768**，里面角色实际只有 **~600px** 高 | PIL 实测 |

于是 `contentSize()` 报的是 `1200`，而贴图里真实角色只有 `600` —— **正好 2 倍**。`SCREEN_FACTOR = 0.5` 就是把这两个数硬拧回来的补偿。

**这解释了当时观察到的全部现象**：

- 「比值**恒为 0.50**」← `实际角色高 600 ÷ geometry 声明的 1200 = 0.5004`
- 「探针报 300px → 屏幕上量到 155px」← 探针报的是 `c.h × scale`（geometry 空间，300），屏幕上是真实高度（150；量出 155 是肉眼误差），**300 × 0.5 = 150 ✓**
- 「探针报 375px → 量到 188px」← 375 × 0.5 = **187.5 ✓**（这个几乎零误差）
- 「把 `resolution` 从 devicePixelRatio 改成 1 也不变」✓ —— 因为根因跟 resolution 一点关系都没有

**顺带解释了 `walk.scale = 0.52`**：走路那批 PNG 一直是 1536×1536（与它自己的 geometry 一致），所以同样公式算出来走路角色是 **400px**，而待机是 **200px** —— 走路凭空大一倍。`0.52` 就是补这个（200/400 = 0.5，实测调到 0.52）。
README §214 记的「缩放系数只有待机的 0.66 倍，屏幕上反而比待机大 1.28 倍，差了约 2 倍 —— 没查到原因」，差的这个 **2 倍就是同一个 768/1536**。

**你现在（16:55~16:58）的改法我验算过，是对的，而且必须三个一起改**：

| 状态 | 表情角色高 | 走路角色高 | 是否自洽 |
| --- | --- | --- | --- |
| 原状态（PNG 768 + SF 0.5 + walk.scale 0.52） | 600×0.3333 = **200px** | 1200×0.3333×0.52 = **208px** | ✅ 一致 |
| 只把 SF 改成 1（PNG 还是 768） | 600×0.1667 = **100px** | 1200×0.1667 = **200px** | ❌ 一大一小 |
| 只把 PNG 换成 1536（SF 还是 0.5） | 1200×0.3333 = **400px** | 1200×0.3333×0.52 = **208px** | ❌ 一大一小 |
| **现状态（PNG 1536 + SF 1 + 删 walk.scale）** | 1200×0.1667 = **200px** | 1200×0.1667 = **200px** | ✅ 一致 |

**可移植性结论（这条是这次审计最该带走的一句话）**：
这三个量全是**"素材内部比例"**，随工程一起走。`host.clientWidth` 是 CSS 像素，Pixi 的 `resizeTo: host` + `autoDensity: true` 让 canvas 的 CSS 尺寸恒等于宿主 CSS 尺寸（我在打包产物里核过 `AbstractRenderer.resize` 的实现），**`devicePixelRatio` 根本不参与布局**。
→ **换 100% / 125% / 200% 缩放，角色大小不会变；换 Mac / Linux 也不会变。**「换 DPI 角色大小就错」这个担心，按当前代码不成立。

**但真正该挂在墙上的风险是这个（🟠 中，可维护性/可移植性）**：

- **在哪**：`FramePet.jsx` 的 `SCREEN_FACTOR` 旁边那段注释仍写着「实测值 0.5 / 根因还没查明 / TODO 查明根因后删掉」，而代码已经是 `= 1`。**注释与代码脱节，下一个人会照着旧注释把 0.5 改回去。**
- **换机器会怎样**：机器换不动它，但**换素材会**。`归一化帧.py` 里把画布写死 1536×1536 的那处常量、以及按这个尺寸重采样的那处 —— **流水线本身只会产出 1536**。那批 768 的 PNG 是流水线之外手工降采样出来的（大概为了压体积），降采样时没人同步改 `geometry.json`。
- **怎么修**：
  1. 删掉 `SCREEN_FACTOR` 常量与那段旧注释，同时在 `FramePet.jsx` 的 `SCREEN_FACTOR` 处和 `归一化帧.py` 的画布常量旁边写一句：**「geometry.json 的画布尺寸必须等于 PNG 的实际像素尺寸，两者不同则角色大小按比例错」**；
  2. 给 `contentSize()` 加一道自检：`if (geo.canvas_w !== tex.width) console.warn(...)`（**要报出来，不能静默**）—— 这一条能保证下次再有人降采样素材时，问题当场暴露而不是靠肉眼量屏幕；
  3. `petAnimations.js` 和 `归一化帧.py` 的注释还写着「画布 768×768 / 窗口 220×300」，现在是 1536 / 220×420，顺手改掉。
- **连带耦合（🟢 低但容易踩）**：`styles.css` 里气泡的 `bottom: 218px` 是**手算的**「`IDEAL_H`(200) + 18」。改 `FramePet.jsx` 的 `IDEAL_H` 时必须一起改这里，否则气泡会离开头顶。两处都已写了互相提醒的注释，保持住。

### 1.2 `ANIMATIONS.walk.scale = 0.52`

已在 §1.1 一并说清：它是同一个 768/1536 问题的补丁，**不是机器相关量**。你 16:57 已经把它删掉了（`petAnimations.js` 的 `walk` 块现在只剩 `frames/fps/loop/sway/geo`），删得对。

> 附：那段「0.92 是试出来的起始值」的注释随 `scale` 一起没了，正常。

## 2. 🔴 高风险（换机器**必然或极可能**出问题）

### R1. 没有安装包 —— 演示完全依赖"演示机上装好了 Node + 带了 node_modules"

- **在哪**：`桌面\desktop\启动桌宠.bat` 里 `call npm run dev` 那一行、`package.json` 的 `scripts` 块（只有 `dev`/`build`/`start` 三个脚本，**没有 electron-builder / electron-forge**）、`desktop\docs\启动说明.md` §3.4 也已自认「打包：做不到」
- **为什么和机器有关**：`npm run dev` 要求目标机器上有：① Node.js ≥18 和 npm；② `desktop\node_modules\`（实测 **370 MB**，其中 `node_modules\electron\dist\electron.exe` 是必须的二进制）；③ 打包时的 Vite dev server（默认端口 5173）。这三样**都不随源码走**（`.gitignore` 把 `node_modules/` 和 `out/` 都忽略了）。
- **换机器会怎样**（按可能性排序）：
  - 演示机上没装 Node → 黑窗口一闪，报 `'npm' 不是内部或外部命令`，**然后窗口就关了**（`启动桌宠.bat` 末尾的 `pause` 还得再敲一下才看得到错）；
  - 拷了源码没拷 `node_modules` → `Cannot find module 'electron-vite'`；
  - **换 Mac / Linux**：把 Windows 的 `node_modules` 整个拷过去**一定不能用**（`electron.exe` 是 Windows x64 二进制，`node_modules\electron\path.txt` 也指向它）→ 必须在新机器上 `npm install`，而那需要网络 + 国内要设 `ELECTRON_MIRROR`；
  - 双击的是 `.bat`（Windows 专有）→ Mac/Linux 上根本没法双击，得手动 `npm run dev`。
- **怎么修**（按性价比排序，都来得及做）：
  1. **今晚就在演示机上把环境跑通一遍**（这一步不能省，其余都是它的备选）：装 Node LTS → 把整个 `desktop\`（含 `node_modules`，370MB，U 盘够）拷过去 → 双击 `.bat`。同是 Windows x64 时这一步就完事了；
  2. 想更稳：先在本机 `npm run build` 生成 `out\`（18MB）一起拷过去，演示机用 `npm run start` 跑 —— **不依赖 dev server，端口冲突问题也没了**。注意 `npm run start` **不会重新编译**，拷过去之前一定要先 build 一次；
  3. 想彻底解决：`npm i -D electron-builder` 打一个 portable exe（今晚时间够呛，建议放到演示后做）。
- **提醒**：`desktop\docs\启动说明.md` §二已经写了 `ELECTRON_MIRROR` 的镜像配法，拷过去的时候**把 `docs\` 一起带上**。

### R2. 对话面板写死 380×620 —— 屏幕不够高时底部被切掉

- **在哪**：`desktop\src\main\index.js` 的 `win:set-chat-open` handler 里 `const w = 380; const h = 620`、同处的展开夹取、`safeSetPosition()` 的夹取、以及收起分支
- **为什么和机器有关**：面板高度是**固定的 620 个 CSS 像素（= DIP）**。屏幕的 DIP 高度 = 物理像素 ÷ 缩放比例，所以**屏幕越小、缩放越高，DIP 高度越小**。而夹取逻辑只夹了**上边界**：
  ```js
  const nx = Math.min(x, workArea.x + workArea.width - w)
  const ny = Math.max(workArea.y, y - (h - PET_H))   // ← 只有 max，没有 min 到底边
  ```
  窗口从角色的位置往上长 200px，**没有校验"面板底边是否还在工作区内"**。
- **换机器会怎样**：工作区高度小于 620 DIP 时，面板下沿落到屏幕外。按内容顺序（`App.jsx` 里从上到下是：气泡 → 语音条 → 状态条 → 教学动作条 → 取消/正常回复/加载中/报错/重连 → 输入框 → 事件日志），**被切掉的正好是最下面的按钮、输入框和日志**。

  | 演示机 | 屏幕 DIP 高（扣任务栏后） | 面板 620 是否装得下 | 后果 |
  | --- | --- | --- | --- |
  | 1920×1080 @100% | ~1040 | ✅ | 正常 |
  | 1920×1080 @150% | ~680 | ✅ | 正常 |
  | 2560×1440 @200% | ~672 | ✅ | 正常 |
  | **1366×768 @125%** | **~574** | ❌ 差 46px | 事件日志被切 |
  | **1366×768 @150%** | **~472** | ❌ 差 148px | **「正常回复」那排按钮和输入框都点不到** |
  | 1920×1080 @175% | ~577 | ❌ 差 43px | 事件日志被切 |

  （"768 高的笔记本 + 125% 缩放"是很常见的出厂设置，这个组合有真实命中概率。）
- **怎么修**：
  1. 展开时按工作区夹取高度（一行的事）：
     ```js
     const h = Math.min(620, workArea.height - 8)
     const x = Math.min(x, workArea.x + workArea.width - w)
     const y = Math.max(workArea.y, Math.min(y - (h - PET_H), workArea.y + workArea.height - h))
     ```
     收起时把 `y + (620 - PET_H)` 同步改成用同一个 `h`（`main/index.js` 的 `win:set-chat-open` 收起分支）；
  2. 或者把面板做成可滚动/自适应高度（改动大，不建议今晚动）；
  3. **兜底方案（不改代码）**：演示机如果是 768 高的笔记本，把系统缩放临时调到 **100%**（设置 → 显示 → 缩放），面板就装得下了。
- **需实测**：具体切掉几个按钮，取决于演示机的实际任务栏高度，建议到现场开一次面板看一眼。

## 3. 🟠 中风险

### R3. TTS 只找 `python` —— Mac/Linux 上默认叫 `python3`

- **在哪**：`main\index.js` 的 `PY` 常量（`process.env.DEEPPROF_PYTHON || 'python'`）、以及 `runSay()` 里的 `execFile(PY, ...)`
- **为什么和机器有关**：Windows 上 `python` 是常规命令名；**macOS 和绝大多数 Linux 发行版只提供 `python3`，没有 `python`**（Ubuntu 从 20.04 起就不再提供）。而 `desktop\docs\启动说明.md` 给的覆盖方法是 `set DEEPPROF_PYTHON=py`，那是 Windows 的 bat 语法，Mac/Linux 上要写 `export`。
- **换机器会怎样**：`execFile` 直接 ENOENT → `runSay` 返回 `{ok:false}` → `tts.js` 静默退回系统合成音。**不会崩、不会报错**，只是神经语音（晓晓）永远用不上，音色退回"客服播报"。在 Mac/Linux 上这个问题**必然出现**（除非手动设环境变量）。
- **怎么修**：在 `main\index.js` 的 `PY` 常量处把"一个名字"改成"一串候选"，启动时探测一次并缓存：
  ```js
  const PY_CANDIDATES = process.env.DEEPPROF_PYTHON
    ? [process.env.DEEPPROF_PYTHON]
    : (process.platform === 'win32' ? ['python', 'py'] : ['python3', 'python'])
  ```
  依次 `execFile(cand, ['-c', 'import edge_tts'])`，第一个返回 0 的胜出；全失败就整体跳过神经语音（省掉后面每次 20 秒的空等）。顺带在 `启动说明.md` 里补一句 Mac/Linux 的写法。

### R4. 神经语音要联网，首次合成最长等 20 秒（而且是在"回复已经显示出来"之后）

- **在哪**：`main\index.js` 的 `runSay()`（`timeout = 20000`）、`tts:synthesize` handler；`tts.js` 的 `tryEdge()`、`speak()` 里 `await tryEdge(...)` 之后才回退
- **为什么和机器有关**：`edge-tts` 走微软的在线端点（`say.py` 里的 `edge_tts.Communicate(...).save(...)`）。**演示现场的网络是最不可控的变量** —— 校园网认证页、会场 WiFi、手机热点限速，都会让这次 TCP 连接挂住。
- **换机器会怎样**：网络不通时，`speak()` 会**先把 20 秒超时等满**，然后才退回系统语音。用户看到的是：文字早就流式显示完了，**声音过 5~20 秒才开口**，而且开口时用的是另一个音色。第一句尤其明显（没有缓存）。另外 `say.py` 的合成结果要一次性拿回整个 mp3（`main\index.js` 的 `tts:synthesize` 返回 `data:audio/mpeg;base64,...`），长回复下这一步本身也要 1~3 秒。
- **怎么修**：
  1. **接到 `tts:selftest` 上**：这个通道（`main\index.js` 的 `tts:selftest` handler）和 `preload\index.js` 里对应的暴露都写好了，但**渲染端没有任何调用方**（`启动说明.md` §四也承认了）。启动时自检一次、把结论缓存在主进程，失败就在本次会话里**直接走系统语音**，用户不用等那 20 秒；
  2. 把 `timeout` 从 20000 降到 6000 —— 正常合成 1~3 秒内必然返回，6 秒不返回基本就是网络挂了；
  3. 演示兜底：如果现场网络没把握，**提前在对话面板里点一下「🔇 自动朗读」关掉自动朗读**，改用「朗读最新回复」手动触发，就不会在讲解流式文本时被卡住。

### R5. 系统语音兜底：`ttsSupported()` 只检查"API 在不在"，不检查"有没有声音"

- **在哪**：`tts.js` 的 `ttsSupported()`、`loadVoices()`（兜底 1 秒后返回**空数组**）、`pickVoice()`（挑不到中文音色返回 `null`）、以及 `speak()` 里 `voice` 为 null 时只设 `u.lang = 'zh-CN'` 就 speak 的两处；界面提示在 `App.jsx` 的语音条
- **为什么和机器有关**：Chromium 的系统语音是**调用操作系统的语音引擎**：Windows 用 SAPI（一般自带 Yaoyao/Huihui），macOS 用 `say` 的语音（中文语音包**要单独下载**），**Linux 用 speech-dispatcher，很多桌面环境下 `getVoices()` 直接返回空数组**。
- **换机器会怎样**：Linux 上（或没装中文语音包的 Windows/macOS）：`ttsSupported()` 返回 `true` → 界面上**不会**显示「本机不支持语音合成」→ 但 `getVoices()` 是空的、`pickVoice()` 返回 null → `synth.speak(u)` 要么静默什么都不发生，要么触发 `onerror` → **桌宠一声不吭，而界面上看起来一切正常**。这正是「失败样例」里最难查的那类问题（不报错、没表现）。
- **怎么修**：
  1. 让 `speak()` 在 `loadVoices()` 拿到空数组时回调 `onState('unsupported')`（一个函数调用的事），`App.jsx` 的语音条就会显示「本机不支持语音合成」，演示时一眼能看出是环境问题不是代码坏了；
  2. `tts.js` 的 `voiceReport()` 已经写好了（返回"支持与否 + 中文音色清单 + 最终选了谁"），**接一个诊断按钮或启动日志**，看现场用哪个音色；
  3. 演示兜底：Windows 上确认「设置 → 时间和语言 → 语音」里有中文语音；Mac 上确认「系统设置 → 辅助功能 → 朗读内容 → 系统声音」里下载了中文语音。

### R6. 只认主屏（`screen.getPrimaryDisplay()`），且不监听显示器变化

- **在哪**：`main\index.js` 的窗口初始位置、`safeSetPosition()` 夹取、`bringHome()`、`wanderOnce()`、开面板夹取、bench 探针（无所谓）
- **为什么和机器有关**：`PrimaryDisplay` 是**操作系统的"主显示器"设定**，不是"桌宠现在在哪块屏上"。演示现场大概率会接**投影仪或外接显示器**，而在 Windows 上它们可能被设成主屏，或者把小人的窗口留在扩展屏上。
- **换机器会怎样**：
  - 演示机接了投影 → 小人的初始位置落在主屏右下角。如果主屏是笔记本内屏、投影是扩展屏，**投影上看不到桌宠**（评审看不到东西）；反过来如果投影被设成主屏，桌宠会出现在投影上，笔记本这边看不见；
  - 演示中途插拔显示器 / 改缩放 → 代码里**没有任何 `screen.on('display-metrics-changed' / 'display-added' / 'display-removed')` 监听**，`winW/winH` 和已算好的位置都不会重算，窗口可能停在已经不存在的工作区坐标上；
  - 小人被拖到副屏后按「回到原位」（`bringHome()`）→ 会被**强行拉回主屏**，用户会觉得"它自己跑回去了"。
- **怎么修**：
  1. 「归位」和漫游落点改成按**窗口当前所在的那块屏**算：`screen.getDisplayNearestPoint(win.getPosition())` 或 `getDisplayMatching(win.getBounds())`，一处替换五处（`safeSetPosition` / `bringHome` / `wanderOnce` / 开面板夹取）；
  2. 加一个 `screen.on('display-metrics-changed', () => bringHome())` 兜底，显示器一变就把小人拉回可见区域；
  3. **今晚的兜底（不改代码）**：演示前把投影设成「复制」而不是「扩展」，并且提前按一下 `Ctrl+Alt+Shift+D`（归位）确认小人在主屏可见。

### R7. `RigPet` 的 `resolution` 与它自己的注释**正好相反**

- **在哪**：`desktop\src\renderer\src\RigPet.jsx` 的 `resolution` 那一段，注释写的是

  > ⚠️ 固定 1，不要用 devicePixelRatio。这个组件每帧要合成【三张】642×1024 的贴图……这是"漫游时掉帧"最主要的一处开销。

  而实际代码是 `resolution: window.devicePixelRatio || 1`（同段的注释又在说"真正的开销优化是上面的 `resolution: 1`"）。**注释描述的优化从来没生效过。**
- **为什么和机器有关**：`devicePixelRatio` 就是系统缩放比例。DPR=1 时每帧填充 3 × 642×1024；DPR=2 时（200% 缩放）是 **4 倍像素量**，即约 790 万像素/帧，还要乘漫游时的窗口移动。
- **换机器会怎样**：在 **200% 缩放**或 4K 屏（Windows 常默认 150%~200%）上，切到分层 rig 模式（右键菜单「换成分层走路」）后，**漫游时明显掉帧**，而开发机（150%）上感觉不出来。不影响逐帧模式（默认路径，`FramePet.jsx` 的 `resolution` 用 DPR 是对的 —— 那边注释里说明了原因：源图大，DPR 下才是逐像素对齐）。
- **怎么修**：按注释的本意改成固定 `resolution: 1`，或者在 200% 机器上实测后再决定；无论如何**注释和代码要统一**，否则下一个人不知道该信哪个。改完在 100% 和 200% 两台机器上各走一圈对比。

### R8. 托盘是唯一的兜底出口，而它在 Linux 上可能根本不显示

- **在哪**：`main\index.js` 的 `createTray()`、两个全局快捷键的注册、关窗口 = 隐藏的 `close` 拦截、`quitApp()`
- **为什么和机器有关**：`Tray` 在 Linux 上依赖桌面环境的 StatusNotifier/AppIndicator（GNOME 默认**不显示**传统托盘图标，除非装扩展）；`globalShortcut` 的注册**可能被别的程序占用**（代码里已经用 ✅/❌ 日志兜住了）。
- **换机器会怎样**：Windows 上基本没事（托盘一定会出现）。Mac 上托盘图标显示在菜单栏，但内嵌的是**彩色 32×32 PNG**，不是 macOS 惯用的 template image，会显得偏大偏色 —— 能用，不好看。**Linux 上**：托盘不显示 + 快捷键被占 → 关闭路径只剩"在小人身上右键 → 退出"，而一旦开了「点击穿透」（`App.jsx` 的 `toggleThrough`），小人点不到、菜单也出不来 → **只能去杀进程**。
- **怎么修**：
  1. macOS：给托盘图标准备一份单色 template 版本，并 `icon.setTemplateImage(true)`；
  2. Linux：不指望托盘，把「退出」同时放进对话面板的可见位置（现在只有右键菜单里有）；或加 `--enable-features=...` 之类的兼容开关（视发行版而定）；
  3. **今晚的兜底**：不管哪台机器，演示前先在终端记一句 `taskkill /F /IM electron.exe`（Mac/Linux：`pkill -f electron`），万一退不掉能救场。

### R9. `hitTest` 的 `crossOrigin` 在 `file://`（prod 模式）下可能拿不到像素

- **在哪**：`desktop\src\renderer\src\hitTest.js` 里 `img.crossOrigin = 'anonymous'` 那一行、以及 `catch → resolve(null)` 的分支
- **为什么和机器有关**：dev 模式页面在 `http://localhost:5173`（`main\index.js` 用 `ELECTRON_RENDERER_URL` 区分 dev/prod），图片同源，取像素没问题；prod 模式走 `loadFile`（`file://`），而 `file://` 在 Chromium 里是**不透明源** —— 给 `file://` 图片设 `crossOrigin='anonymous'` 会走 CORS 检查，很可能直接 `onerror`。
- **换机器会怎样**：如果演示机上用 `npm run start`（跑 `out\`）而不是 `npm run dev`，掩码可能全部为 null → `hitTest()` 的 `if (!mask) return true`→ **整块矩形都算命中** → 角色周围那一大片透明区域也挡住桌面图标，点击穿透形同虚设（"桌宠挡路"）。dev 模式不受影响。
- **怎么修**：去掉 `crossOrigin` 那行（同源/`file://` 都不需要它），或者干脆从已经加载好的 Pixi 贴图取像素（`app.renderer.extract`），少一次网络请求。
- **需实测**：这条我没法静态证实（取决于 Electron 版本对 `file://` 的 CORS 处理）。验证方法：`npm run build && npm run start`，看终端有没有 `[渲染进程]` 转发的图片加载错误，然后在小人旁边的透明区域点一下桌面图标试试。

### R10. 单实例锁：有残留实例时，双击 `.bat` 会"什么都没发生"

- **在哪**：`main\index.js` 的单实例锁（`requestSingleInstanceLock`）那一段
- **为什么和机器有关**：不是机器差异，是**"换一台电脑演示"这个场景本身就容易带残留状态** —— 昨天在演示机上跑过没退干净、或者团队里有人先开了一个。
- **换机器会怎样**：第二个实例只打印一行 `[桌宠] 已经有一个实例在跑了，这次启动直接退出` 就退了，然后 `.bat` 走到 `pause`。用户看到的现象是：**黑窗口开了、闪了几行字、小人没出来**。而且这个"退出"还会把已经在跑的那个实例叫回屏幕底边（单实例分支里会 `bringHome()`），进一步像是"动了一下又没反应"。
- **怎么修**：
  1. 残留实例的清理写进演示前置检查：任务管理器里搜 `electron`，全杀；
  2. 更好的是把这一行日志改成用户能看见的东西（`dialog.showMessageBox`：'桌宠已经在运行了，看屏幕右下角'），这样"没反应"变成"有解释"；
  3. `.bat` 里在 `npm run dev` 之前加一句 `taskkill /F /IM electron.exe >nul 2>&1`（粗暴但有效，演示场景够用）。

## 5. 查过、明确无问题的方向（不用再花时间）

| 系统语音兜底 | ✅ SAPI 自带中文 | ⚠️ 中文语音包需单独下载 | ❌ 常见为**无声**且界面不提示（见 R5） |

**若演示机真是 Mac**：最省事的方案是**从队友里换一台 Windows 笔记本**（本模块的目标平台就是 Windows，`启动说明.md` §一也这么写的）。
**要真支持 Mac**，今晚至少要动这几处：R3（python3 候选）、R5（空语音列表要提示）、R8 的 macOS 托盘 template、以及补 `app.on('before-quit', () => { reallyQuitting = true })` 让 Cmd+Q 走通。Linux 还要另算透明窗口和托盘的账。
