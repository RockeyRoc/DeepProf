## 问题 1｜取消到底发哪个事件？（**最要紧**）

同一个语义，两边发了**不同的事件名**：

| | 发什么 | 位置 |
| --- | --- | --- |
| **Mock**（前端自演） | `agent.failed({reason: "cancelled"})` | `desktop/src/main/index.js` 的 `cancel()` |
| **真后端** | `agent.cancelled({reason: "cancelled"})` | `runtime/core/agent.py:91` |

`runtime/core/events.py:37-38` 里 `AGENT_CANCELLED` 和 `AGENT_FAILED` 是**两个并列的独立类型**，
不是同一个事件的两种写法。

**为什么会出这个岔子**：前端契约开头声明「`source_of_truth` = MockRuntime」，
契约是照 Mock 写的，于是写下了「agent.failed 是取消状态的**唯一**表达方式」——
这句话对 Mock 成立，对真后端**不成立**。

**如果不管它会怎样**：照契约实现前端的人只会监听 `agent.failed`。
真后端取消一轮时前端什么都不做 → 状态**永久卡在 streaming**、朗读也不停。
而「流式文本与语音可停止」是 §16.4 的验收项。

**建议：统一到 `agent.cancelled`（也就是改 Mock）。** 理由：
1. 后端已有测试锁死这个名字（`tests/integration/test_runtime_turn.py:232` 断言 `AGENT_CANCELLED`），改后端要动测试；
2. 语义上「取消」和「失败」确实是两回事 —— 取消是用户主动的，不该混进 error 通路；
3. 前端两个都接了，改 Mock **表现零变化**，不会影响现有演示。

**要你回**：同意统一到 `agent.cancelled` 吗？如果同意，我改 Mock 的 `cancel()`。

## 问题 2｜`agent.cancelled` 不在「终结事件」名单里

`api/routes/sessions.py` 里：

```python
_TERMINAL_TYPES = frozenset(
    {EventType.AGENT_TURN_COMPLETED.value, EventType.AGENT_FAILED.value}
)   # ← 没有 AGENT_CANCELLED
```

同一文件 `_SSE_EVENT_NAMES` 里也没有 `AGENT_CANCELLED`，所以它会落到默认值
`event: event`（其他终止类事件是 `done` / `error`）。

**目前没暴雷**：流是靠订阅关闭（`_on_done` → `close_stream`）结束的，不是靠这个名单。
但「终结事件名单」漏了一项终态，属于将来一定会咬人的那种缺口 —— 比如有人往
`_event_stream` 里加逻辑时按名单判断。

**要你回**：要不要把 `AGENT_CANCELLED` 补进 `_TERMINAL_TYPES`，
并在 `_SSE_EVENT_NAMES` 里给它一个明确的事件名？

## 问题 3｜后端没有「显式取消」接口（**这个可能最影响验收**）

我把 `api/` 翻了一遍：**没有** `POST /sessions/{id}/cancel` 之类的接口。
现在唯一的取消手段是**客户端断开 SSE 连接**。

但这带出一个死结：

```
前端想取消 → 只能断开 SSE
          → 服务端才触发 CancelledError → 发 agent.cancelled
          → 可这条 SSE 已经断了，这个事件发不出去
          → 前端永远收不到「已取消」的确认
```

也就是说：**真后端下，前端没法在流上得知「取消成功了」**，只能靠重连回放
（`GET /sessions/{id}/events`）事后补。前端现在只能本地自己认定「我点了取消」。

Mock 之所以看起来正常，是因为它由**前端自己**触发 `cancel()` 并本地发事件 ——
这条路在真后端上不存在。

**要你回**：要不要加一个显式取消接口？比如 `POST /sessions/{id}/cancel`，
让前端能：① 主动请求取消 ② 在同一条流上收到 `agent.cancelled` 作为确认。
这条直接关系到 §16.4「流式文本与语音可停止」怎么验收。
